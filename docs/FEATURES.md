## Built — Receptionist/Nurse SOAP Pre-entry (Task #6)

**2026-09-21 (DEV only; no commit/push/deploy).** Receptionists and Nurses can pre-enter the patient's history and vitals before the Doctor sees the patient. The entry is preliminary: the Doctor still reviews and edits everything in the normal consultation workspace.

- **Receptionist and Nurse (identical behaviour)** may enter: the 7 Subjective fields (chief complaint, history of present illness, past medical history, family history, social history, review of systems, subjective notes) and the vitals (blood pressure, pulse, respiratory rate, temperature, height, weight, SpO2, pain score, head circumference; BMI is computed server-side).
- **Doctor-only, never offered and rejected by the server**: physical examination, clinical findings, clinical impression, differential diagnosis, assessment notes, treatment plan, patient instructions, follow-up recommendation, referral notes, ICD-10 fields; also complete/sign and the full `/soap` endpoint (Owner/Administrator remain view-only there).
- **Where**: Queue -> "Enter Vitals" (`ReceptionVitalsDialog`, now scrolling with two sections) and the New Queue pre-queue step (`PreQueueVitalsStep`), both using the shared `features/consultation/components/intake-fields.tsx`. Existing behaviour is preserved: Save and Print / Save and Close, the required-vitals gate and asterisks and live BMI in the pre-queue step, the empty-form save guard (unchanged, see limitations), and the BUG-024 error messages.
- **Server-side enforcement**: `PUT /consultations/{id}/soap/subjective-objective` uses `extra="forbid"` (`SoapNoteSubjectiveObjectiveUpsert`), so any unsupported key returns **422** (no silent ignore); the field list no longer contains physical examination / clinical findings. `GET /consultations/soap-suggestions` now allows Receptionist/Nurse for `chief_complaint` only and returns **403** for every Doctor-only field (an unsupported field is still 422).
- **Chief complaint suggestions reuse Task #2**: the same `SoapSuggestionInput`/`SuggestionInput` (multiline, selection stays editable, custom text always works); no other reception field asks for suggestions.
- **Changed-fields-only saves (BUG-043)**: reception saves and the Doctor autosave/Save Progress send only the fields changed since the form loaded or last saved. The Doctor autosave hook keeps a baseline (`changedSoapFields`) and ignores a slower response for a different consultation. Unspecified fields are omitted (never `null`); an explicit `null`/empty is sent only when a user clears a field.
- **No migration; no change to consultation completion/signing (BUG-042 untouched).**

## Built — Personal SOAP Phrase Suggestions (Task #2 enhancement)

**2026-09-22, DEV only - not committed/pushed as part of the Tasks #1-#9 release (commit `3a1604c`).** The Task #2 clinic-learned suggestions satisfy "has the clinic used this phrase before", but not the Doctor's actual ask - "I have already typed/used this, let me pick it again instead of retyping it." This adds three DOCTOR-SPECIFIC layers on top of the unchanged clinic + starter list, ordered by priority in the dropdown: **My Phrases** (explicitly saved), **Recently Used** (the Doctor's own recent values, no 2-patient threshold), then **Clinic Suggestions** (Task #2, unchanged) and **Starters** (unchanged). A phrase is shown once, in the highest section that has it.

- **My Phrases (favorites)**: the Doctor can save the exact line/segment they are typing with a small "☆ Save '...' to My Phrases" action under the dropdown, or star (★/☆) any suggestion row. Saving is idempotent (re-saving the same phrase, case/whitespace-insensitive, does nothing new) and capped at 30 phrases per field. Un-favoriting (★ Remove) is a hard delete - it is a personal preference, not clinical data.
- **Recently Used**: derived read-only from the Doctor's OWN prior `soap_notes` / `diagnoses` values (via `Consultation.doctor_id`), across any consultation status (Draft/InProgress/Completed/Signed) so it works mid-visit, not only after signing. No 2-different-patient threshold (that safeguard stays on the clinic list only). Newest first, capped at 10.
- **Doctor-specific and field-specific scope**: every list is scoped to `(clinic_id, doctor_id, field)`. A phrase saved for Chief complaint never appears under Treatment plan or any other field; one Doctor never sees another Doctor's phrases, even in the same clinic.
- **Multiline unchanged**: exactly like Task #2's clinic suggestions, matching/selecting/saving acts on the LINE the caret is on - the rest of a multi-line field (e.g. Treatment plan) is untouched, and a whole multi-line block is never saved as one phrase.
- **Privacy safeguards**: every phrase (favorite or recent) passes the same Task #2 `is_suggestible` filter (no emails, URLs, phone-like numbers, patient/visit/invoice ids, UUIDs, or obvious test junk), must be a single line of 80 characters or less, and Recently Used additionally drops any phrase that contains the patient's own first/middle/last name. Responses carry suggestion text only - never a patient, consultation, visit, SOAP-note or doctor id.
- **Endpoints** (siblings of the unchanged `GET /consultations/soap-suggestions`): `GET /consultations/soap-suggestions/personal?field=&q=&limit=` -> `{field, favorites:[{text}], recent:[{text}]}`; `POST /consultations/soap-suggestions/favorites` `{field, text}` (201 new / 200 already-saved / 422 invalid phrase / 409 over the 30-per-field cap); `DELETE /consultations/soap-suggestions/favorites?field=&text=` (204 / 404). All three require the **Doctor role with a linked `doctor_id`** - Receptionist, Nurse, Owner, Administrator and every other role get 403, so Task #6's Receptionist/Nurse `chief_complaint` suggestion access is unaffected and cannot reach personal phrases.
- **Migration**: `0046_soap_phrase_favorites` - one new additive table (`clinic_id`, `doctor_id`, `field`, `phrase`, `phrase_key`, unique on `(clinic_id, doctor_id, field, phrase_key)`, indexed on `(clinic_id, doctor_id, field)`). No existing table changed; no historical SOAP data touched.
- **Frontend**: `SuggestionInput` gained optional `sections`/`personal`/`onFocus` props (a flat `suggestions` list still renders exactly as before when they are omitted, so Task #8's prescription fields and the Receptionist/Nurse Task #6 fields are unchanged); a new `PersonalSoapSuggestionInput` wraps it for the Doctor page; `SoapSuggestionInput` gained an opt-in `personal` flag used only on the Doctor consultation page's SOAP and ICD-10 fields.
- **Files**: backend `api/v1/soap_personal_phrases.py`, `services/soap_personal_phrase_service.py`, `repositories/soap_personal_phrase_repository.py`, `models/soap_phrase_favorite.py`, `schemas/soap_suggestions.py` (extended), `alembic/versions/0046_soap_phrase_favorites.py`; frontend `PersonalSoapSuggestionInput.tsx`, `use-soap-personal-phrases.ts`, `suggestion-sections.ts`, `SuggestionInput.tsx` (extended), `SoapSuggestionInput.tsx` (extended), `consultation-api.ts` (three functions), and the consultation page (`personal` prop on Chief complaint / ICD-10 code / ICD-10 description).
- **Live DEV acceptance (2026-09-22, real Doctor UI, Maria Santos, Demo Clinic, `VIS-20260917-000001`)**: My Phrases (save-from-typed-text, appears under My Phrases, select + edit stays fully editable), Recently Used (a saved value reappeared as Recently Used on refocus, newest-first ordering confirmed with two values), Clinic Suggestions and Starters both still present, field isolation (a Chief complaint favorite did not appear under Treatment plan), multiline (Treatment plan: only line 2 changed, lines 1/3 untouched), unfavorite (removed, confirmed gone via the API), free text, ICD-10 code/description suggestions (no diagnosis added), 375px mobile layout (no horizontal overflow, dropdown scrollable, stars usable), and a read-only check that the personal response holds only `{field, favorites, recent}` text with no patient/consultation/visit/doctor id. Consultation stayed `InProgress`, unsigned, 0 diagnoses throughout.
- **Cleanup**: the temporary Chief complaint and Treatment plan text was cleared via Save Progress and the favorite was removed; a before/after DB comparison showed the consultation identical to its pre-demo state (both fields already held `''`, not `NULL`, before this session, so no new empty-string discrepancy was introduced). No diagnosis was created and no unrelated data changed.
- **Known limitations**: Recently Used only reflects a note's LAST saved value per field per consultation (there is no edit history, so a phrase since edited away will not reappear); the 30-favorite cap is per field with no UI to browse past it other than removing one; a Receptionist/Nurse's own text saved on a Doctor's visit can appear in that Doctor's Recently Used once the Doctor's own consultation is saved (accepted by design - it is the Doctor's own patient record); this build has not been committed or pushed (kept separate from the Tasks #1-#9 release commit `3a1604c`).
## Built — Doctor SOAP Autosuggest / Auto-input (Task #2)

**2026-09-21.** Clinic request: "Doctor wants auto-input/autosuggest fields, especially SOAP." Hybrid design: **clinic-learned suggestions** (from the clinic's own existing SOAP/diagnosis entries) plus a **small static starter vocabulary**. No migration and no schema change; the SOAP persistence chain (`use-soap-autosave` → `PUT /consultations/{id}/soap` → `SoapNoteUpsert` → `save_soap` merge-write → `soap_notes`) is untouched.

- **Where**: Doctor consultation page, SOAP tab, and the Diagnosis tab.
- **Fields with suggestions (8)**: chief complaint, physical examination, clinical findings, clinical impression, differential diagnosis, treatment plan, patient instructions, follow-up recommendation. **Left as plain textareas**: history of present illness, past medical history, family history, social history, review of systems, additional subjective notes, assessment notes, referral notes (patient-specific narrative). **Diagnosis tab**: ICD-10 code and ICD-10 description (a new optional description input was added next to the existing code input) - learned values only; **no ICD-10 catalog is bundled**.
- **Control**: the Task #8 `SuggestionInput` was extended with a `multiline` (textarea) mode rather than adding a second suggestion framework. Focusing/typing shows matching suggestions; selecting one replaces **only the line the caret is on** (other lines are preserved) and puts the caret at the end of the insertion; the field stays fully editable and any custom text is always valid. Single-line behaviour (Task #8 prescription fields) is unchanged. Read-only viewers get disabled fields and no suggestion request.
- **Static starters**: `features/consultation/lib/soap-vocabulary.ts`, the same intentional pattern as Task #8's `prescription-vocabulary.ts` - a few generic documentation phrases per field, no patient data, no canned narratives, not a clinical recommendation. **Learned values always come first**, duplicates (case-insensitive) collapse.
- **Endpoint**: `GET /consultations/soap-suggestions?field=<field>&q=<query>&limit=<1-20, default 10>` -> `{"field": ..., "suggestions": [{"text": ...}]}`. Read-only; clinic-scoped by `clinic_id`; gated to Doctor, Owner and Administrator (the SOAP edit roles), who may ask for any allowlisted field; **Task #6 later extended this**: Receptionist and Nurse may ask ONLY for `chief_complaint`, and every other field - the Doctor-only ones - is a 403 for them; `field` must be on an allowlist (the 8 SOAP fields + `icd10_code` + `icd10_description`, anything else is a 422 and no column name is ever taken from the client). Text only - no patient or consultation identifiers and no counts.
- **Learned-suggestion safeguards**: only values used in consultations of **at least 2 different patients** (several visits by one patient do not count); case-insensitive de-duplication with whitespace normalized; **80 characters or less**; single-line values only; the requested `q` is a literal substring match (SQL wildcards are escaped); ordered by number of distinct patients (most first), then alphabetically, so results are deterministic; obvious identifying/junk values are screened out (email addresses, URLs, phone-like numbers, patient/visit/invoice/UUID-style identifiers, long code-like tokens except in the ICD-10 code field, and a few unmistakable test artifacts such as "asdf" or "test ..."). This is not medical-text classification, and stored SOAP/diagnosis data is never modified, normalized or deleted - the filtering only affects what is *suggested*.
- **Files**: backend `api/v1/soap_suggestions.py`, `services/soap_suggestion_service.py`, `repositories/soap_suggestion_repository.py`, `schemas/soap_suggestions.py` (+ router registration); frontend `SuggestionInput.tsx` (extended), `SoapSuggestionInput.tsx`, `use-soap-suggestions.ts`, `soap-vocabulary.ts`, `consultation-api.ts` (one function), and the consultation page (the eight `Field`s and the diagnosis inputs only; the Task #7 address block is unchanged).
- **Known limitations**: suggestions are learned per exact phrase, so a clinic needs the same short phrase used for two different patients before it appears (a new clinic sees only the static starters); multi-line entries do not contribute learned values (only single-line values are learned); the browser fetches the clinic's top 20 per field and filters them as the doctor types; selecting an ICD-10 code does not auto-fill its description; the static starter lists are conservative examples, not a clinical vocabulary, and are edited in code (a clinic-editable list is a possible follow-up via `system_settings`); the Receptionist/Nurse SOAP pre-entry dialog (Task #6) is not changed.

## Built — YAKAP Billing Report (Task #4)

**2026-09-21.** Clinic request: a billing report for YAKAP patients, by week / month / year / custom range. Page: **Billing → YAKAP Billing Report** (`/billing/yakap-report`; sidebar link for Owner, Administrator and Cashier).

- **Population (clinic decision)**: invoices of patients whose standing flag `Patient.is_yakap_beneficiary = true`. **`Queue.visit_classification` never decides inclusion** - the two YAKAP concepts stay independent. So a YAKAP patient's Regular-classified visit IS included, and a non-YAKAP patient's Yakap-classified visit is NOT. The page carries this note: "YAKAP billing report is based on patients marked as YAKAP beneficiaries. Visit classification (Yakap/Regular) does not determine inclusion." No name/free-text matching is used, and no new YAKAP field or migration was added.
- **Date basis**: `Invoice.invoice_date` (Asia/Manila-based since Task #9). Weekly/Monthly/Yearly resolve against the clinic's own "today" through the same clinic-timezone helper that dates invoices (`InvoiceService._clinic_today`, default Asia/Manila), so there is no second timezone mechanism. Weekly = Monday-Sunday of the current week, Monthly = the current calendar month, Yearly = the current calendar year, Custom = any inclusive start/end. All are inclusive on both ends; the resolved range is shown on the page.
- **Invoices counted**: not deleted, and not Cancelled or Draft. Patients that are archived still count (their billing history does not disappear).
- **Summary (server-side, over the WHOLE filtered set, never the visible page)**: YAKAP Patients = distinct patients with a qualifying invoice; Consultations = `ConsultationFee` invoice items; Laboratory Services = `Laboratory` invoice items (only real billing items - a lab order that has no invoice line is not counted); Total Billed = sum of invoice grand totals (one per invoice, so a multi-item invoice is never multiplied); Total Paid = sum of **Completed** payments on those invoices (voided payments excluded; a completed visit is never treated as paid); Outstanding = the sum of the invoices' existing `balance_due`.
- **Detail table**: **one row per invoice** (Date, Patient, Visit, Invoice, Services list, Billed, Paid, Balance, Status), newest first, 20 per page with Previous/Next. Services are listed inside the row instead of as extra rows, so a paid pay-first lab and a late lab charge each appear once.
- **Search**: patient name/number, invoice number or visit number; it narrows the rows and the summary together.
- **Export / print**: **Export CSV** (the existing `AnalyticsService.export_report_csv`; contains every row of the filtered population, not just one page) and **Print** (`window.print`, same approach as the receipt: only the report body prints).
- **Access / isolation**: `GET /billing/reports/yakap` and `/yakap/export`, gated to Owner, Administrator and Cashier (`require_billing_manage_role`); every query is clinic-scoped. Read-only; no schema change, no migration.
- **Known limitations**: Weekly/Monthly/Yearly are always the CURRENT period (use Custom for a past one); Total Paid ignores refunds because the existing refund flow is separate from payment status; the report shows what the invoices hold now, so a late lab charge raises the billed total of its original invoice date.
- **DEV limitation**: no DEV clinic has an invoice for any YAKAP patient (Pilot Community Clinic's only YAKAP patient has no billing), so the positive population could only be exercised by the automated tests; live DEV shows the correct empty state and that Regular-patient invoices are excluded. No billing data was created for this task.

## Built — Patient List: YAKAP / Regular View (Task #5)

**2026-09-20.** Clinic request: "Create a view where only YAKAP patients can be seen."

- **UI**: a new **Patient type** select on the Patients page - *All Patients* / *Regular Patients* / *YAKAP Patients* - next to the existing gender/status/sort filters. It combines with the search box, gender, status, sort and date filters, and resets to page 1 when changed.
- **Authoritative field**: `Patient.is_yakap_beneficiary` (the patient's standing PhilHealth YAKAP status, editable in the patient form). YAKAP = `true`, Regular = `false`. Nothing is inferred from names, notes or free text.
- **Not the queue field**: `Queue.visit_classification` (Yakap/Regular) is a per-encounter value and is unchanged. The two are deliberately independent - a Regular-flagged patient can have a Yakap-classified visit and vice versa; this task never reads, syncs or rewrites either value from the other.
- **Server-side**: `GET /patients?is_yakap_beneficiary=true|false` (omitted = all). The filter is part of the same query that builds the page and the `total`, so search and pagination are correct across pages (not a client-side filter over page 1).
- **Empty state**: "No YAKAP patients found." / "No Regular patients found." (with a search: `No YAKAP patients match "..."`); regular patients are never shown under the YAKAP filter.
- **No schema change, no migration**, no new role; access control is the existing patient-view gate and tenant scoping.
- **Not included**: the YAKAP billing report (Task #4).
- **Known limitation**: the Demo Clinic's DEV data has 30 Regular patients and no YAKAP patients, so the positive YAKAP list was only exercised by the automated tests; see docs/TESTING.md for what was verified live.

## Built — Billing: Every Completed Patient Billed, Newest First (Task #9)

**2026-09-20.** Clinic request: "in Billing make the most recent patient appear on top" and "make sure all completed patients need to pay." Investigation found the list was already newest-invoice-first, so the real gaps were around it.

**Clinic decisions applied**: "recent" = latest **completed visit**; plain recent-first (no unpaid-first pinning); auto-create a bill for a completed visit that has none; billing dates in **Asia/Manila**; a lab charge that finishes after the patient already paid **reopens the bill**.

- **Sort**: Billing now orders by when the visit was completed (`Visit.check_out_time`), falling back to the invoice's creation time when the visit isn't completed yet; `id` breaks ties.
- **Load more**: the list was hard-capped at 20 rows with no way to see older bills; it now has a "Load more" button (filters reset it).
- **Every completed patient gets a bill**: consultation-complete and quick-complete already did; setting a visit to Completed directly (`PATCH /visits/{id}/status`) now creates the bill too (idempotent, so paid and walk-in lab pay-first visits are untouched).
- **Manila dates**: new invoices are dated by the clinic's own timezone (`Clinic.timezone`) instead of UTC, so a bill made at 7:50 AM Manila is dated that day. Billing's "Today / This Week / This Month" filter uses Manila too (other tabs are unchanged).
- **Late lab charge**: a doctor-ordered lab completed after the bill was Paid or Partially Paid used to be silently dropped (or blocked). It is now added: a Paid bill becomes Partially Paid with only the new charge outstanding, earlier payments and receipts are untouched, and it is audit-logged. Walk-in / pay-first lab orders are deliberately excluded - their charge is already on the bill.
- **Backfill (DEV only, dry-run by default)**: `backend/scripts/task9_billing_backfill.py` re-dated existing invoices to Manila (119) and created bills for 9 completed visits that had none. **Not run on production** - it needs the clinic's sign-off first (the back-filled July bills appear as unpaid).
- No schema migration.
- **Known limitations**: the sort key is `Visit.check_out_time`, so back-filled bills (visits completed in July) sit near the bottom, not the top; invoice *numbers* keep their original UTC-based date prefix, so a number can differ by a day from the displayed Manila date (e.g. `INV-20260917-000001` displays 09/18/2026); reopened bills have no "additional lab charge" badge (clinic chose none); Load more grows the page size (re-fetches the first N rows) rather than appending pages; the Billing date filter's timezone is fixed to `Asia/Manila` in the page, not read from the clinic setting; the backfill script has no environment guard - it runs against whatever `DATABASE_URL` points at (dry-run by default).
- **Acceptance status**: implementation verified in DEV; **clinic-side UI acceptance still required**. The live DEV workflow (visit completion, payments, lab orders/results) was driven through authenticated calls to the app's real endpoints from the browser tab, not through UI clicks or UI automation; invoice auto-creation and all totals were produced by the app. The Billing page (order, Load more, Manila dates, Today/This Week/This Month) was inspected in the live UI, with the filter presets selected by setting the native select's value in the page. Screenshot capture timed out, so no screenshots are recorded. Not called production-ready.

## Built — Prescription Searchable Dropdowns / Autocomplete (Task #8)

**2026-09-20.** Clinic request: doctors were retyping the same values on every prescription line. Previously every `PrescriptionItem` field (medicine, strength, dosage, frequency, route, duration) was plain free text, not linked to the `Medicine` catalog, with only a small hardcoded `COMMON_MEDICINES` name list (explicitly not a formulary) for medicine suggestions.

**Now (data-entry convenience only - no clinical logic)**:
- **Medicine**: live type-to-search against the real `Medicine` catalog (`GET /medicines?q=…&is_active=true`, reusing the same `createCrudHooks` the Medicines admin page uses; Doctor already has view access via `INVENTORY_VIEW_ROLES`). Deliberately filtered only by `is_active`, **not** by stock - an out-of-stock medicine is still a legitimate thing to prescribe. Each catalog row is one generic+brand+strength+form combination, so the dropdown lists the actual available strengths (e.g. "Amoxicillin (Amoxil) — 500mg" and "Amoxicillin — 250mg").
- **Strength / Form**: selecting a catalog medicine auto-fills its `strength` and `dosage_form` (still editable); both also offer suggestions drawn from the searched catalog rows.
- **Dosage / Frequency / Route / Duration**: searchable suggestion inputs backed by one central list (`features/clinical-orders/lib/prescription-vocabulary.ts`) - UI vocabulary examples only, **not** a clinical recommendation or controlled vocabulary. Any custom value can still be typed; nothing is restricted.
- The hardcoded `COMMON_MEDICINES` list is no longer used by the prescription form.
- New reusable `SuggestionInput` component (type freely OR pick a suggestion).

**Schema**: one additive nullable column, `prescription_items.dosage_form` (migration `0045_prescription_item_dosage_form`), a snapshot like `strength`/`generic_name`/`brand_name`. Every historical prescription keeps `dosage_form = NULL` and renders exactly as before; no backfill, no rewrite. `generic_name`/`brand_name` snapshot fields (already on the model) are now populated on catalog selection. No new API endpoint.

**Not built (deliberately)**: a clinic-editable admin screen for the Dosage/Frequency/Route/Duration lists - the smallest change that meets "stop retyping" was a central static list; making it clinic-configurable (via the existing `system_settings` key/value store) is a natural separate follow-up.

**Safety**: nothing recommends a drug or dose, suggests treatment from symptoms, or changes a selection for the doctor.

**Verified live in DEV** (real Doctor UI): searched "Amox" → real catalog entries; selected Amoxicillin → strength 500mg + form Capsule auto-filled; picked dosage/frequency/route/duration from suggestions; added a second item (Paracetamol, custom free-text frequency) - the two rows stayed independent; saved as one prescription (`RX-20260920-000001`), reloaded, all values persisted in their own columns; pre-existing free-text prescriptions ("TID", "PRN", no form) still read fine. DEV note: the DEV Medicine catalog was empty, so 3 DEV-only test medicines were added via the Medicines admin (they were saved inactive by mistake and corrected to active).

## Built — Doctor Workspace: Patient Address in Consultation View (Task #7)

**2026-09-18.** Clinic request: "Include address at doctors workspace, consultation view" — so the doctor can see where the patient lives without leaving the consultation to open the full Patient record.

## Built (Foundation Stage)

### Multi-tenant Authentication (Phase 2)

- JWT-based auth with short-lived **access tokens** and rotating, opaque **refresh tokens**; refresh tokens are hashed at rest (`refresh_tokens`/sessions table) and rotated on every `refresh` call — reuse of a revoked/rotated token revokes the full session chain.
- Endpoints wired against the real database: `login`, `logout`, `refresh`, `register`, `forgot-password`, `reset-password`, `verify-email`, `resend-verification`.
- `login`/`refresh` set the refresh token as an `HttpOnly`, `Secure`, `SameSite=Strict` cookie; `remember_me` on `login` controls session length (short session-only vs. extended ~7-day cookie).
- **Account lockout:** after repeated failed logins, `users.failed_login_attempts`/`locked_until` trigger a temporary lockout (`403`) independent of successful-login resets.
- **Password reset / email verification:** token-based flows (`password_reset_tokens`, `email_verification_tokens`) — tokens are hashed at rest, single-use, and time-limited. **TODO:** actual SMTP email delivery of the links is not yet wired up; token issuance/consumption logic is fully implemented (see [`SECURITY.md`](SECURITY.md), [`API.md`](API.md)).
- **Rate limiting:** Redis-backed limits enforced on `login`, `forgot-password`, `resend-verification`, and `refresh`.
- Passwords hashed with `passlib` using argon2 (bcrypt fallback supported).
- Every authenticated request carries `clinic_id` (tenant context) inside the JWT claims, resolved via a FastAPI dependency and injected into the repository layer.
- Login events (success/failure) and lockout events are written to `audit_logs`.
- Roles seeded at migration time: **Owner, Administrator, Receptionist, Doctor, Nurse, Cashier, Laboratory, Pharmacy, Viewer**, joined to `permissions` via `role_permissions`.

### User Management (Phase 2)

- Tenant-scoped CRUD for staff users under `/api/v1/users` — list/search (by name/email/username/role/status/branch), fetch, create, update, disable, enable, and admin-initiated password reset.
- Extended user profile fields: `middle_name`, `mobile_number`, `username`, `status` (`active`/`disabled`/`pending`), `profile_photo`.
- Create/update/disable/enable/admin-reset-password are role-gated to Administrator/Owner; a user may self-update their own non-privileged fields.
- Disabling a user immediately revokes all of their active refresh tokens/sessions.
- `frontend/src/features/users/` provides the corresponding UI (list/search table, create/edit forms, disable/enable actions) inside the `(dashboard)` route group.

### Patient Management (Phase 3)

- Tenant-scoped, branch-aware master patient database under `/api/v1/patients` — the record every future clinical module (queue, appointments, billing, laboratory, pharmacy, medical records, reports) will reference by `patient.id`.
- **Patient number generation:** sequential, clinic-scoped numbers (`PAT-000001`, ...) generated by a configurable `PatientNumberGenerator` backed by a per-clinic counter row in `system_settings` (not a raw DB sequence), so a clinic's numbering scheme (prefix/padding) can be customized later without a migration. Counter increments are safe under concurrent creates via `SELECT ... FOR UPDATE`.
- **Duplicate detection:** on create and on edits that change name/DOB/mobile, the backend checks for existing patients with the same first+last name and birth date, or the same mobile number. Matches are returned as a structured warning (`duplicates: [...]`) instead of the created/updated record; an Owner/Administrator can resubmit with `?override=true` to save anyway. Every other manage-capable role can create/edit but cannot bypass the warning.
- **QR check-in code:** a signed, opaque `clinic_id:patient_id:signature` token (HMAC-SHA256, app secret) generated per patient and stored in `qr_code`, exposed via `GET /patients/{id}/qr`. Verifiable by a future queue/appointment scanner without a DB round trip. Actual QR *image* rendering is intentionally deferred (see [`DATABASE.md`](DATABASE.md)) — only the payload string is returned today.
- Full CRUD + search: `GET /patients` supports free-text search (patient number, legacy patient id, name, mobile, email), filters (branch, gender, status, age range, date-registered range, last-visit range), sort (newest/oldest/alphabetical/recently visited), and limit/offset pagination with a total count.
- Archive/restore (`POST /patients/{id}/archive` / `/restore`) is a business-status change (`status: Active/Archived`), fully separate from soft-delete (`is_deleted`) which is not exposed on this API.
- Presigned-URL stub for patient photo upload (`POST /patients/{id}/photo`) matching the same Supabase Storage stub pattern used for user profile photos in Phase 2 — TODO: wire to real Supabase Storage + thumbnail generation once a bucket is provisioned.
- Every create/update (with a field-level diff)/archive/restore writes an `audit_logs` entry via the shared `AuditService`.
- Role gating: all clinic roles can view patients; Owner/Administrator/Receptionist/Doctor/Nurse can add/edit; Owner/Administrator/Receptionist can archive/restore; only Owner/Administrator can override a duplicate warning.
- Import/export extension points only: `services/patient_import_export.py` defines `PatientImporter`/`PatientExporter` ABCs (CSV/Excel/legacy-import, CSV/Excel/PDF-export) — no importer/exporter is implemented yet.
- `frontend/src/features/patients/` provides the corresponding UI: searchable/filterable/sortable patient list with debounced search, add/edit form (Identity/Contact & Address/Medical Info sections) with duplicate-warning confirmation, and a patient profile page with Overview/Personal Information/Medical Notes tabs plus "coming soon" placeholder tabs for Visit History, Appointments, Billing, Laboratory, Prescriptions, Documents, and Audit Logs.

### Clinic Configuration & Master Data (Phase 4)

Configuration/master-data CRUD consumed by future Queue, Appointments, Billing, Medical Records, and Reports modules. No queue/ticket, appointment/booking, or billing logic is implemented here — see [`ROADMAP.md`](ROADMAP.md) for those.

1. **Clinic Settings** — singleton-per-clinic settings (address breakdown, TIN/license, timezone/language/currency/date-format/time-format, status) added directly onto the existing `clinics` row (no separate table). `GET`/`PUT /clinic-settings`, Owner/Administrator write, all roles read.
2. **Branches** — extended the existing `branches` table with `code` (unique per clinic), `contact_number`, `email`, `manager_id` (FK to `users.id`), `status`. Full CRUD + search/pagination under `/branches`.
3. **Departments** — `department_code` (unique per clinic), name, description, color, status. `POST /departments/seed-defaults` optionally seeds 8 standard departments (General Medicine, Pediatrics, OB-Gyne, Internal Medicine, Dental, Laboratory, Radiology, Physical Therapy) for a brand-new clinic; 409s if the clinic already has departments.
4. **Doctors** — `doctor_code` auto-generated by a clinic-scoped `DoctorCodeGenerator` (parallel to `PatientNumberGenerator`, same `system_settings`-counter + `SELECT ... FOR UPDATE` pattern, kept separate to avoid touching the shipped Phase 3 patient code path), name/license/specialization/department/branch/fee/photo fields. `doctor_schedules` is a plain weekly availability table (`day_of_week`, `start_time`, `end_time`) with full CRUD under `/doctors/{id}/schedules` — architecture only, no appointment-slot generation or booking logic.

7. **Queue Settings** — pure configuration: `queue_settings` (prefix, max daily queue, reset time, allow-walkins, allow-priority-lane), unique per `(clinic_id, branch_id)` so a clinic can configure clinic-wide (`branch_id=null`) or per-branch. `priority_types` is a small per-clinic reference list (Senior, PWD, Pregnant, Emergency, VIP by default via `POST /queue-settings/priority-types/seed-defaults`). No ticket-issuing/calling/serving logic.
8. **Operating Hours** — `operating_hours` keyed by `(clinic_id, branch_id, day_of_week)`, with opening/closing time and an optional lunch-break window. Upsert via `PUT /operating-hours`.
9. **Holiday Calendar** — `holidays`: name, date, recurring flag, closed/half-day flags, optional `branch_id` (null = clinic-wide). Full CRUD + year/branch filtering under `/holidays`.
10. **Clinic Branding** — kept on the `clinics` row alongside settings (logo/favicon/login-background URLs, primary/secondary color, theme) rather than a separate table, since clinics do not need branding history/versions in this phase. `PATCH /clinic-settings/branding`; presigned-upload stub at `POST /clinic-settings/branding/{asset}/upload` (`logo`/`favicon`/`login-background`), same pattern as the Phase 2/3 photo-upload stubs.

Cross-cutting: every module is tenant-scoped (`clinic_id`), soft-deletable, role-gated (Owner/Administrator for writes; broad read access for operational roles via `require_config_view_role`/`require_config_manage_role` in `core/dependencies.py`), paginated/searchable/filterable where it's a list resource, and every create/update/delete/restore writes an `audit_logs` entry via the shared `AuditService`.

## Built — Phase 6: Visit (Encounter) Management

The Visit is the central transaction every future clinical/billing module (SOAP notes, diagnosis, prescriptions, laboratory, billing) will attach to. - Queue → Visit integration: `QueueService.create_queue()` calls `VisitService.create_visit_for_queue()` internally in the same DB transaction as the queue-ticket insert, then links `queue.visit_id` ↔ `visit.queue_id`. The Phase 5 `POST /queues` request/response contract stays backward compatible (`visit_id`/`visit_number` are additive, optional response fields) — existing queue list/status-transition/cancel/slip endpoints are unmodified.
- Visit status machine (Registered → Waiting → Called → InConsultation → Completed, plus Cancelled/NoShow) with legal-transition checks, writing both to `visit_timeline_events` (domain timeline) and the generic `audit_service` (compliance audit trail) on every write.

- Search/filter/paginate by patient, doctor, department, status, visit type, and date range; free-text search across visit number, queue number, and patient name/number.
- Frontend `features/visits/`: Visit List page (search + date-range preset/status/visit-type filters, paginated, row click → details), Visit Details page (summary card, chronological Timeline component, clearly-labeled "coming soon" placeholder cards for SOAP Notes/Diagnosis/Prescription/Laboratory/Billing/Attachments/Audit Log — same pattern as the Phase 3 patient-profile placeholders), Patient Details "Visit History" tab (was a Phase 3 stub, now a real paginated visit table), Sidebar nav entry between Queue and Users.

## Built — Phase 7: Doctor Workspace

The doctor's daily driver screen: today's assigned patients, quick visit actions, and a read-focused visit viewer with editing-lock coordination. Built entirely on top of the Phase 6 Visit lifecycle — no parallel status machine.

All Visit status changes are delegated to `VisitService.change_status()` (the Phase 6 legal-transition table) — this service only layers consultation-session tracking, doctor_activity logging, lock management, and WebSocket broadcast on top.
- `GET /doctor-workspace/dashboard` (real computed Waiting/Called/Serving/Completed Today/Cancelled/No-Show counts and average consultation duration) and `GET /doctor-workspace/queue` (today's assigned visits, with live-computed waiting time); Owner/Administrator can view any doctor's workspace via an optional `doctor_id` query param or see all doctors' visits by omitting it.

- Realtime: reuses the Phase 5 `queue_connection_manager` / `/ws/queues/{clinic_id}` WebSocket channel (rather than a second connection manager) to broadcast `visit.called`/`visit.consultation_started`/`visit.consultation_completed`/`visit.status_changed`/`visit.lock_acquired`/`visit.lock_released`, so a future TV Display can subscribe to the same channel.

- Frontend `features/doctor-workspace/`: Doctor Dashboard page (stat cards, Today's Queue table with contextual Call/Recall/Start/Complete/No-Show/Cancel actions and live-computed waiting time), Sidebar nav entry, and the existing Phase 6 Visit Details page extended (not duplicated) with a lock banner ("Currently being edited by Dr. ___") and a doctor-actions panel visible to Doctor/Administrator/Owner viewers.

**Explicitly out of scope for this phase:** SOAP Notes, Diagnosis, Prescription, Laboratory, Billing, Medical Records, Appointments, TV Display — only clearly-labeled placeholder sections referencing them as future work.

## Patient Portal (Phase 18)

A THIRD, structurally separate portal alongside the clinic-staff portal and Phase 15's SaaS Administration Portal — patients are a third class of principal, not a clinic `User` and not a `PlatformAdminUser`. Follows the Phase 15 precedent exactly: a dedicated auth table, a JWT with a distinct `type` claim, and a completely independent FastAPI dependency chain.

- **Patient auth** (`patient_accounts` — a new one-to-one table linked to the existing `patients` table by `patient_id`, chosen over adding password columns directly to `Patient` since login-credential data has a different write-path/threat-model than clinic-managed demographic data): login by email OR mobile number + password, a JWT with `"type": "patient_access"`/`"patient_refresh"` (never `"access"` or `"platform_admin_access"`), and a new `get_current_patient` FastAPI dependency that is the only thing that accepts it — verified mutually rejected against `get_current_user` and `get_current_platform_admin` in both directions.

- **Reception integration**: no new table. ## Post-RC1 — Phase 2 Milestone 2: Cloud Backup (One-Way Sync)

Builds real, upload-only local-to-cloud synchronization on top of Milestone 1's Connectivity Service. Local is always the source of truth; the cloud can never write back to or overwrite local data; no clinic workflow is ever blocked, slowed, or altered by sync failing or lagging.

- **`sync_jobs` table** (`backend/app/models/sync_job.py`, migration `0023_sync_jobs`) — the persistent local→cloud upload queue: `entity_type`, `record_id`, `operation` (create/update/delete), a JSONB `payload` snapshot, `status` (pending/in_progress/completed/failed), `retry_count`, `next_retry_at`, `last_error`, `completed_at`, `duration_ms`.
- **`sync_queue_service.enqueue(...)`** (`backend/app/services/sync_queue_service.py`) — the single shared entry point every hooked entity service calls at the end of its own successful mutation. Uses its own separate DB session/transaction (not the caller's), called only after the caller's own commit already succeeded, and never raises — any failure here is logged and swallowed so the primary clinic operation is completely unaffected. Wired into: Patient (create/update), Visit (create via queue and pre-queue draft, update, status change), Queue ticket (create, update, status change), SOAP note (Subjective/Objective save, full save), Prescription (create), Laboratory order (create, release) and result (enter results), Payment (record), Shift (start, close).
- **Background Sync Worker** (`backend/app/services/sync_worker_service.py`) — an asyncio loop (started/stopped in `main.py`'s lifespan, same shape as `connectivity_service.py`) that runs every `SYNC_WORKER_INTERVAL_SECONDS` (default 30s), draining `sync_jobs` oldest-pending-first (plus any `failed` job whose backoff window has elapsed) against the cloud Backup API — but only when `connectivity_service`'s own reachability state reports `cloud_status == "up"` (reused, not duplicated). On failure: exponential backoff (`SYNC_RETRY_BASE_SECONDS * 2^retry_count`, capped at `SYNC_RETRY_MAX_SECONDS`), `retry_count` incremented, `next_retry_at` set, error recorded — the job is never discarded. On success: marked `completed`, `completed_at`/`duration_ms` recorded. **Internet Recovery hook**: `connectivity_service.refresh_state()` calls `sync_worker_service.trigger_sync_now()` the moment `cloud_status` transitions from down/not_configured → up, so a queued backlog drains immediately instead of waiting for the next tick.
- **Cloud Backup API** (`backend/app/api/v1/backup.py`) — what a *cloud-hosted instance of this same codebase* (pointed at `CLOUD_DATABASE_URL`) exposes for a clinic's local sync worker to call. `POST /api/v1/backup/{entity_type}` only — no GET/PUT/PATCH/DELETE, so nothing can ever read back, overwrite, or mutate on command; this channel is strictly local→cloud upload. Authenticated with a distinct shared secret (`X-Sync-Api-Key` header checked against `settings.CLOUD_SYNC_API_KEY`) — NOT any of this codebase's three existing JWT principal types. Upserts into a new `synced_records` table (`backend/app/models/synced_record.py`) keyed on `(clinic_id, entity_type, record_id)` — a document-style backup store (JSONB payload snapshot per record) rather than a fully-normalized relational mirror, since replaying into the cloud's own `patients`/`visits`/... tables would require independently mirroring every foreign-keyed parent row (clinics, users, doctors, ...) in dependency order, which is out of scope for a one-way *backup* (see the file's docstring for the full rationale). Genuinely deployable as-is to a real cloud instance — nothing assumes it's running alongside a local instance.
- **Dashboard expansion** — `GET /api/v1/system/status` and the System Status page now also show: Pending Sync Jobs, Retry Queue (jobs with `retry_count > 0`), Total Uploaded Today, Average Sync Time, Last Successful Sync, Last Failed Sync (with reason). Frontend polling on this page tightened from 30s to 10s (this page only).
- **`DEPLOYMENT_MODE=local` (the default, unchanged) behavior**: the sync worker loop still runs but `_ready_to_sync()` always returns `False` when `CLOUD_API_URL`/`CLOUD_SYNC_API_KEY` are unset, so no network I/O or `sync_jobs` mutation ever happens — a local-only clinic is behaviorally identical to before this milestone. Sync jobs are still enqueued (best-effort, harmless additive rows) even in local mode, since enqueueing happens unconditionally at the point of mutation; only the *draining* is gated on cloud reachability.

## Post-RC1 — Vaccination Administration

Fills a real gap in the existing Phase 9 Clinical Orders module: a `Vaccination`-category order already existed as an order type a Doctor could create, but nothing let anyone actually record it as *given* — the generic order-status-update endpoint was hardcoded to the assigned Doctor only, with Receptionist explicitly read-only and no Nurse permission at all.

- **Doctor still orders** a vaccination via the unchanged `POST /consultations/{id}/orders` with `order_category: "Vaccination"` — no change to that flow.
- **New: administering it is a broader, separate permission** from the doctor ordering it. `VACCINATION_ADMINISTER_ROLES = {Owner, Administrator, Doctor, Nurse, Receptionist}` — any Nurse or Receptionist in the clinic may administer a vaccination a doctor ordered, not just the ordering doctor, matching real clinic staffing (explicit client decision).
- **New `vaccination_administrations` table** (migration `0024`), auto-created 1:1 on top of the order the same way Laboratory's `laboratory_orders` table is (see `docs/DATABASE.md`), capturing vaccine name, dose, lot number, injection site, route, notes, who administered it, and when — a real structured immunization record, not just a generic order-status flip.
- **New `/vaccinations` dashboard page** (sidebar nav, all roles): a worklist of pending vaccination orders with an "Administer" action opening a small form for the administration details, plus Administered/Cancelled history. Reuses the existing System Status/Laboratory Dashboard visual pattern.
- Administering also advances the underlying Order to `Completed` (cancelling advances it to `Cancelled`), so it reads correctly everywhere the Order is shown (Doctor Workspace, visit timeline).
- **One real bug found and fixed while building this**: BUG-032 — a pre-existing missing `selectinload(User.role)` in the platform-admin tenant-user-management service caused a 500 on a genuinely fresh backend session (masked in tests by stale identity-map caching); fixed and verified live.

**Live-verified**: a real Doctor ordered a vaccination via the API; the workflow record auto-created correctly; a real, newly-created Nurse account (distinct from the ordering Doctor) administered it end-to-end through the actual browser UI, with dose/lot/site/route/notes all persisting and displaying correctly; the underlying Order mirrored to `Completed`; a Cashier-role account was correctly rejected with 403 attempting the same action; full `test_clinical_orders.py` + `test_platform_admin.py` suites (26 tests) re-run against the disposable test DB with zero regressions.
